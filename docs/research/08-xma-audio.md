# XMA and Windows audio output

## Audio path in ReXGlue 0.10.1

The USA XEX imports 16 XMA context functions for allocation, initialization, enable and disable, and input and output buffer management. ReXGlue implements the context functions through its XMA decoder. An enable command can decode inline and wake the `XMA Decoder` worker. The context mutex serializes decode, disable, and release. Release clears the Guest context and resets the decoder state. The pinned SDK has no equivalents for the Canary `use_dedicated_xma_thread` and `xma_decoder` options. [XEX imports](02-dump-inspection.md) · [SDK XMA imports](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_audio_xma.cpp) · [SDK decoder](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/audio/xma_decoder.cpp) · [SDK context](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/audio/xma_context.cpp)

The Guest registers its mix callback at `XAudioRegisterRenderDriverClient`. A separate SDK `Audio Worker` calls that function and the Guest submits six planar big-endian float channels through `XAudioSubmitRenderDriverFrame`. The SDL driver copies each 256-sample-per-channel buffer before queuing it and folds the channels to stereo if the device opens with one or two channels. `XAudioQueryDriverPerformance` is a stub. The SDK returns a fixed speaker configuration, unchanged category volume, and a zero mask for category volume changes. [Host import audit](../../src/kernel_audit.cpp) · [SDK XAudio exports](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_audio.cpp) · [SDK worker](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/audio/audio_system.cpp) · [SDK SDL driver](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/audio/sdl/sdl_audio_driver.cpp)

## Unattended Windows playback check

The November 15, 2026 test used the USA disc, stock ReXGlue runtime DLL, the scripted Free Skate controller, default 60 Hz Guest timing, and RTV with draw extent estimation. The controller loaded a copied test skater, selected the Community Center spawn, and sent eight pushes in Free Skate. A Windows process loopback capture recorded only Port output at 48 kHz stereo. A test-only Host probe counted render submissions and applied the SDK's stereo fold to copies of Guest buffers to measure their peak. The default save directory and normal Port executable were kept outside the instrumented runs. [Scripted controller](04-renderer-performance.md) · [Windows process loopback](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)

- With the default WASAPI path, the named headphones negotiated two channels. Three captures showed startup movie audio followed by output near the capture noise floor in the menu and Free Skate. The in-game music, sound effects and dialogue sliders were up. Free Skate windows measured about −92 to −96 dBFS RMS. The probe still saw about 187–188 Guest buffers per second and nonzero stereo-folded peaks. [Intermittent Windows output investigation #60](https://github.com/TheRealestNwah/skate-recomp/issues/60)
- Changing the SDK stereo LFE weight from 0 to 0.316 and back in the same process did not restore the output. The calculated fold already contained signal from other channels with the default weights.
- Forcing `SDL_AUDIO_DRIVER=directsound` negotiated six channels on the same named endpoint. Windows loopback recorded menu and Free Skate signal. The three five-second windows spanning the push sequence and coast measured −46.9, −43.4 and −46.0 dBFS RMS. A second launch through `run-port.ps1 -DirectSound` negotiated six channels again and produced captured Free Skate audio.
- A later WASAPI run on the same endpoint captured normal game signal during Free Skate before any test signal was enabled. A temporary 750 Hz tone at 0.035 full scale in both front channels yielded a loopback peak of about 0.0205 full scale, consistent with the SDK's default stereo scale of about 0.586. Returning to the original buffers restored game signal.

The maintainer reported having to reapply Windows Volume Mixer mute on each launch. The earlier captures did not record the mixer's per-process state, so those low captures cannot establish a WASAPI defect. **[Inference]** The later run shows that the stock stereo path can carry the expected signal. Reproducing the earlier loss requires holding the process volume and mute state constant.

The normal Port executable also crashed at Guest address `0x0000003C` when a test forced the unavailable SDL `disk` backend. The SDK logged an audio initialization error immediately before the crash. This test establishes a failure to handle backend initialization errors. It did not disconnect or disable the user's endpoint. [Audio startup issue #59](https://github.com/TheRealestNwah/skate-recomp/issues/59)

The Host now stops with exit code 1 and flushes the SDL error and a Port diagnostic if the SDK cannot create the audio driver. Repeating the forced failure produced the two diagnostics and no Guest exception. A muted control run on the default backend opened the endpoint and submitted Guest audio. Both tests used the stock SDK.

## Flickit input

At the default 60 Hz Guest display mode, a test-only Host probe counted the Guest's `XamInputGetState` calls by slot. Menus and Free Skate at Community Center both ran at approximately 60 calls per second per slot across slots 0–3. The connected scripted controller also received about 60 state reads per second. Held right-stick motions scored switch ollies and switch kickflips. The right-trigger sequence did not verify a grab. [SDK input export](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xam/xam_input.cpp) · [Controller baseline](05-m4-baseline.md)

Executive producer Scott Blackwood described 120 Hz sampling during Flickit development. The measured Port cadence is below that target. The retail Guest reaches the import via `0x82BC3AC0` and the wrapper at `0x82DF8C60`. [Original developer interview](https://www.gamedeveloper.com/design/new-tricks-scott-blackwood-talks-i-skate-i-and-i-skate-2-i-) · [Input cadence issue #65](https://github.com/TheRealestNwah/skate-recomp/issues/65)

A November 16, 2026 trace followed that call back to the input callback at `0x82578AA8` and worker at `0x82BBC600` in the USA XEX. The worker rearms a one-shot timer through `NtSetTimerEx`. Its constructor at `0x82BBC228` divides 10,000,000 by the requested rate to obtain the interval in 100 ns units. A probe read the live rate of 60 and interval of 166,666. [USA XEX identification](02-dump-inspection.md) · [SDK timer export](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_threading.cpp)

A test-only hook at `0x82BBC238` changed the constructor argument from 60 to 120. The interval became 83,333 and the Guest made about 120 calls per second for each of slots 0–3 in the menu and at Community Center. Guest swap submissions stayed near 60 per second. Captures showed the skater jumping and flipping the board in response to scripted stick sequences.

The same 240 ms D-pad Down press moved the main-menu highlight from Continue Career to Xbox Live in the 60 Hz control and to Free Skate in the 120 Hz test. The hook was removed from the normal build. [Input cadence issue #65](https://github.com/TheRealestNwah/skate-recomp/issues/65)

The input callback at `0x82578AA8` copies controller snapshots into two 30-entry rings. At 120 Hz polling, publishing every other snapshot to the first ring restored the single-item advance on a 240 ms hold in the main menu and pause menu. Applying the same limit to the second ring alone still skipped Xbox Live. The first-ring test reached Community Center and scored ollies and a heelflip from scripted stick motions.

During Free Skate, the second ring received about 120 snapshots per second and its reader at `0x824C1E18` advanced through them at the same rate. The reader advances to the newest entry before applying its controller state at `0x824C1F08`. In one window, the thread that also submits Guest swaps applied 240 states in 4.05 seconds, about 59 per second.

The first ring applies snapshots on a separate thread. The same thread submits stick coordinates to the gesture matcher at `0x824BEE10`. A probe tracked the mode whose coordinates changed with the scripted right stick. At Community Center, the original 60 Hz worker delivered about 60 samples per second to that mode. A prototype with the first ring at 120 Hz and the second at 60 Hz delivered about 120. The prototype scored an ollie, double heelflip and melon grab. The stock control scored ollies and a heelflip with the same sequence.

The button decoder at `0x82BBCEC0` counts samples for debounce and repeat. The Port doubles those counts for the 120 Hz reader, from 3 to 6 for debounce, 24 to 48 for initial repeat and 12 to 24 for subsequent repeats. The input worker still publishes to the presentation reader every other sample. The 240 ms D-pad test advanced one item in the main and pause menus after scaling the counts. [Port hooks](../../config/skate.toml) · [Input cadence issue #65](https://github.com/TheRealestNwah/skate-recomp/issues/65)

The Port build with these hooks reproduced the 120 Hz right-stick samples, menu navigation and the three scored tricks at the default 60 Hz Guest display mode. It used the stock SDK runtime and a scripted controller. The physical controller baseline still needs to cover trick feel and held menu navigation. [Controller baseline](05-m4-baseline.md)

An offline executable compiled the five Host input hooks with synthetic register values. It checked the 60-to-120 Hz rate override, alternating presentation snapshots, 90 debounce comparisons, and repeat counts for the gesture reader and other callers. Two synchronized threads each retained their own alternating snapshot phase. These checks cover the Host decisions made by the hooks. Physical controller response and release timing remain on the baseline checklist. [Host hooks](../../src/skate_app.cpp) · [Hook sites](../../config/skate.toml) · [Controller baseline](05-m4-baseline.md)

## Streaming smoke test

In one muted run, the controller skated at Community Center, quit Free Skate to the main menu, loaded the Library in Downtown, and skated there. The test-only Host counted 1,857 `NtReadFile` calls requesting about 202 MiB in the first load window and 1,833 calls requesting about 192 MiB in the second. XMA enable calls and audio submissions continued with device output muted. The log recorded no APU warning or error, and the skater responded after each load.

The probe saw physical-memory frees during boot and none through the two load windows. These observations cover two locations and one return to the main menu. The SDK completes the file read before writing the I/O status block and signaling the event. That behavior applies even when the export returns `X_STATUS_PENDING` for an asynchronous handle. [SDK file read](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_io.cpp)

A November 16 follow-up traced the Guest's physical allocations and XMA calls on the build with 120 Hz Flickit sampling. The controller loaded Community Center, returned to the main menu, then loaded the Library and skated. All observed compressed input and decoded output spans fit within two allocations made during startup. Each of the 256 initialized contexts kept the same pair of input buffers and single output buffer. The trace recorded 4,954 context reinitializations, each with a successful `XMADisableContext(wait=1)` after the previous initialization and before reuse. Neither backing allocation was freed during the run. The SDK logged no APU warning or error, and the Port exited with code 0. [SDK XMA imports](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_audio_xma.cpp) · [SDK decoder lock](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/audio/xma_decoder.cpp)

Repeating the two-location run with file I/O tracing recorded 5,577 completed `NtReadFile` calls and 511 MiB read. Every request larger than 1 KiB fit within a tracked physical or virtual allocation. No tracked free overlapped a read in progress, and no completion reported more bytes than requested. This trace covers the kernel allocation ranges and I/O calls. The Guest's suballocations within those ranges and the lifetime of assets after the I/O completes remain unverified. [SDK memory imports](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_memory.cpp)

An offline comparison of the same trace converted the Guest's three physical address aliases to a common offset. The 512 compressed-input spans and 256 decoded-output spans were pairwise disjoint. Sixteen of the 5,577 reads used a physical destination. Their requested and completed byte ranges had zero overlaps with the observed decoder buffers. [SDK physical address translation](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/system/xmemory.cpp#L2350-L2357) · [SDK XMA packet and output block sizes](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/include/rex/audio/xma/context.h#L177-L191)

In the USA XEX, the input refill paths at `0x828ED684` and `0x828ED704` check whether the slot is invalid and copy up to 2 KiB from a source cursor through `0x828ED3B8`. The Guest then calls `XMADisableContext(wait=1)`, marks the slot valid, and enables the decoder. In the trace, all 11,123 calls that marked a refill valid followed a successful waiting disable for the same context and thread at the corresponding call site. [USA XEX identification](02-dump-inspection.md) · [SDK XMA imports](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/src/kernel/xboxkrnl/xboxkrnl_audio_xma.cpp)

An offline executable compiled the Generated packet-copy routine and its Generated scalar-copy and register-save helpers against the pinned SDK headers. With synthetic source bytes, it checked all 16 source alignments and every length from zero through 2,048 bytes, for 32,784 cases. Every copied byte matched the source, both 32-byte destination guards kept their sentinel values, and the stack pointer was restored. The destination was 16-byte aligned, matching the input buffers in the captured trace. This check covers copy behavior with valid memory supplied by the probe. Concurrent decoder access and Guest source ownership still require separate evidence. [USA XEX identification](02-dump-inspection.md) · [Pinned SDK headers](https://github.com/rexglue/rexglue-sdk/blob/v0.10.1/include/rex/ppc.h)

**[Inference]** In the observed XMA path, the Guest reuses a pool of decoder contexts and keeps their backing memory for the duration of play. The waiting disable serializes context reuse with the SDK decoder.
